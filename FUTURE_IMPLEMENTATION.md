## 2. Background job architecture (new since the original plan)

A real BullMQ scheduler architecture now exists — this **supersedes** the original "compute on read" pattern documented in earlier versions of `API.md`/`DATABASE.md` for Twins and Evolution. Both docs still describe the old on-demand pattern in places and need a pass to catch up (tracked in §5 below).

| Job                 | Schedule                                       | What it does                                                                                                                                                                   |
| ------------------- | ---------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `embedding`         | Triggered per-user after `recalculateScores()` | Embeds that user's Parallels; backfills any content items still missing an embedding (fixed this session — previously re-embedded _every_ content item on _every_ run, see §4) |
| `emerging-parallel` | Every 6 hours                                  | Finds all users with interest signals, queues per-user detection, which clusters recent signals and creates novel Parallels                                                    |
| `evolution`         | Every 30 days                                  | Finds all users with Parallels, queues per-user `recalculateScores()` (which also captures an evolution snapshot)                                                              |
| `twins`             | Every 15 minutes                               | Finds all Twin-eligible users, queues every pairwise combination for `saveTwinMatch()`                                                                                         |

**Known characteristic, not a bug**: a brand-new user won't get their first Twin match or emerging-Parallel detection until the next scheduled run fires (up to 15 min / 6 hr respectively). This is the accepted tradeoff of moving to a scheduled-job model instead of on-demand computation — consistent with the blueprint's own "computed by a scheduled job, not on-demand" note for Twins.

## 3. What's genuinely next (priority order)

1. **Quests frontend** — the backend is fully ready and untouched by any bug found in this audit. Pure UI work against a stable API. Natural first pick.
2. **Notifications** — nothing exists yet (no queue, no gateway, no delivery). This is what's silently missing from Streaks: the blueprint's §4.1 calls for a decay warning ("Your Builder streak is about to end 👀"), and there's currently no way to deliver that, or to tell a user about a new Twin match, emerging Parallel, or quest reward without them manually refreshing. No architecture decision needed to start — Socket.IO is already a dependency, unused.
3. **Wrapped + Identity Cards** — blueprint calls this the "single highest-leverage feature" for growth. Needs one real decision before starting: how Identity Cards actually get rendered as images (server-side canvas/SVG vs. a headless-browser approach) — not decided yet.
4. **Communities + Collab** — still pure spec. Lower priority than the above; don't build ahead of actual demand for them.
5. **Roulette** — explicitly deferred until a moderation/safety model exists first (per `DATABASE.md` §4's standing note). Do not build before that.

## 4. Issues found and fixed during this audit

- **Duplicate Twin computation**: `UsersController.getTwins()` was calling `refreshTwinMatches()` (a full on-demand recompute) on _every_ request, on top of the new scheduled job doing the same work independently every 15 minutes. Removed the on-demand call and the now-dead `refreshTwinMatches()` method entirely (plus its tests) — `GET /v1/users/twins` is now read-only, as the scheduler intends.
- **`EmbeddingProcessor` re-embedded every content item in the database on every single user's embedding job**, regardless of whether it already had an embedding — O(users × content_items) instead of O(content_items) total. Fixed to only embed content items where `embedding IS NULL`.

## 5. Known technical debt (not fixed, flagged for awareness)

- **`TwinsProcessor`'s O(n²) pairwise scheduling, every 15 minutes.** Fine at current scale; will queue an excessive number of jobs once the Twin-eligible user count grows past a few hundred. Revisit with incremental/change-triggered recomputation instead of a full pairwise sweep when that becomes real.
- **`InterestSignal.targetType` casing is inconsistent across writers** — lowercase (`'content'`, `'parallel_type'`, `'user'`) vs. uppercase (`'QUEST'`). Not currently a bug (every reader agrees with its corresponding writer's casing), but a latent footgun for the next person who writes a new signal source without noticing the inconsistency. Worth normalizing to one convention before this table gets queried for anything beyond the exact paths that exist today.
- **Verify the Groq model ID (`openai/gpt-oss-120b`) directly against a live call.** If it's wrong or gets deprecated, `GroqParallelNamingProvider` silently falls back to the generic "Emerging Interest" identity — nothing crashes, but the actual AI-naming feature would be quietly non-functional despite looking implemented. This needs a real, live test, not a code read — I can't call the Groq API myself to verify it.
- `API.md` / `DATABASE.md` still describe some of this area (Twins, Evolution) using the older "compute on read" framing superseded by §2 above. Needs a dedicated documentation pass — deliberately not done in this same session to avoid rushing it alongside a live audit.
